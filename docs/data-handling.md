# Data handling

This page says where a team's messages go when the bot runs, where they are stored, and what the code does and does not delete. It was traced from the code on 2026-11-19 (retention and the host table again on 2026-11-20) and names the file for each claim. The code is the source of truth; if this page and the code differ, trust the code and report it.

It is not legal advice and it does not say what your institution allows. It tells you what to take to the people who decide that.

Two later changes are on `main` and have no row of their own in the table below yet: a second model provider (Claude on Microsoft Foundry; `MODEL_PROVIDERS`, [`model-providers.md`](./model-providers.md)) and an email route for operator alerts (`ADMIN_ALERT_ROUTE`; `AGENTS.md`, safety items). Every provider in `MODEL_PROVIDERS` receives what the agent path row lists. Operator alerts by email go through the outbound mail provider row.

"Program repo" is the knowledge-base repo. "Provider's terms" means the code sets no retention there; the contract you hold with that party does.

## Who can read the audit log and the raw mail

The audit log, the mail copies, the `.eml` originals and the extracted attachments are ordinary files in the program repo. The code adds no access control of its own. Whoever can read the repo on the git host can read all of them, including every past version.

- **Make the program repo private.** The code does not check this. A public program repo publishes the team's mail.
- **Repo readers are a different group from allowlisted senders.** A person on the email allowlist can ask the bot questions; they cannot read the repo unless you add them on the git host. A repo collaborator can read every mail from every sender, whether or not that collaborator is on the allowlist. Review both lists.
- **Count the machine identities.** The intake service, the host and the container each hold a credential that can read or write the repo (`AGENTS.md`, "First start"). So does any CI job, site build or integration you attach on the git host.
- **Organization owners and git-host administrators** can usually read private repos. Ask your git host's administrator who that is.
- **The agent can read all of it.** The email group mounts the program repo read-write, so a question from any allowlisted sender is answered by an agent that can open any mail in `discussions/raw/` and any day of the audit log. The prompts tell it what to cite; nothing in the code keeps one sender's mail from an answer to another.
- **The agent can write it too, after the host has committed it.** The host writes and commits each entry in its own repository, out of the agent's reach (`src/host-repo.ts`). Once committed, the file is in the program repo and the agent can commit a change to it. `SPEC.md` section 6: "do not edit the log" is then a rule, not a storage guarantee. Git history is the check.

## Retention and deletion

Traced from the code on 2026-11-20. Three kinds of store behave differently.

**1. Stores with a fixed window.** Run logs and session files (`scripts/cleanup-sessions.sh`), and four SQLite tables (outbox, approval evidence, delivery notes, delivery tracking). The windows are in the host table above. The outbox window covers dead letters too: a mail that failed for good is removed 24 hours after it failed, and a mail that is still queued or can be retried has no end time and is never removed by the window.

**2. Stores on the host with a retention setting.** The default for every key is `0`, which keeps everything: with no retention key set, the host starts no prune and behaves as it did before the keys existed. A value above `0` is a whole number of days; the host then deletes what is older, about a minute after it starts and once a day (`src/retention.ts`, started from `src/index.ts` beside the session cleanup). A negative number, a fraction or text stops the host at startup. Each run writes one line to the host process log with a count per store and no content.

| Store | What is kept when the key is set | Default | Setting | How to delete by hand |
|---|---|---|---|---|
| `messages` table | A message not answered yet (after its chat's cursor), however old; in a chat that needs a trigger word, the messages waiting as context for the next trigger; a message the message loop has not seen; every message of a chat that has no saved cursor and no bot reply; the newest bot reply of each chat, which the host uses to rebuild a lost cursor. Everything else older than the window is deleted. Older replies then no longer appear in the recent-history part of a prompt. | Keep forever | `RETENTION_MESSAGES_DAYS` | Stop the bot; `sqlite3 store/messages.db "DELETE FROM messages WHERE timestamp < '2026-01-01'"`. Do not delete rows newer than the last reply in a chat. |
| `routed_approvals` table | The row itself, always: its key (the path of the mail file), status and dates. For an approval closed or removed before the window the content is cleared: title, sender, approver, subject, the quoted words, the trusted addresses, the hold reason. The row has to stay, because the scan treats an open entry in `discussions/OPEN_QUESTIONS.md` with no row as new and mails the approver; the empty row keeps a reopened entry as inert as it is today. Not touched at all: an approval still waiting on someone, and a closed one with an operator notice or a relay not yet recorded. | Keep forever | `RETENTION_ROUTED_APPROVALS_DAYS` | Stop the bot; clear the same columns on rows whose `status` is `closed` or `removed`. Deleting a row is safe only when its entry is gone from `OPEN_QUESTIONS.md` and will not come back. |
| `scheduled_tasks` and `task_run_logs` tables | Active and paused tasks, always. The approved email-outreach task (`EMAIL_OUTREACH_TASK_ID`). Run records for at least 7 days whatever the value, because the exceptions digest reads 7 days. The newest run record and its task, from which `/health` reports how long ago the scheduler ran. Deleted: one-time tasks that have run, and older run records. | Keep forever | `RETENTION_TASKS_DAYS` | Ask the bot to cancel a task (it deletes the task and its run records), or delete rows while the bot is stopped. |
| Transcript archive, `groups/<group>/conversations/` | Files not named `YYYY-MM-DD-<name>.md`, and sub-folders. The host never reads these files, but the agent is told it may search them to recall earlier conversations, and it loses what is deleted. A file the agent itself saved there under a name of that form is deleted too. | Keep forever | `RETENTION_TRANSCRIPT_ARCHIVE_DAYS` | Delete the files. |
| Telegram files, `data/telegram-uploads/<group>/` and host-written photos in `groups/<group>/attachments/` | A file named in a message not answered yet, with its extracted text. Any file in `attachments/` that the host did not name. After deletion the agent can no longer open an old upload if someone asks about it again. | Keep forever | `RETENTION_UPLOADS_DAYS` | Delete the files. |
| Working-context archive, `data/working-context/<key>.archive.json` | The live file `<key>.json` is never touched. Archive entries without a readable time are kept. The host writes a new one when it next archives. |

| Set-aside container requests, `data/ipc/errors/` | Nothing older than the window. | Keep forever | `RETENTION_IPC_ERRORS_DAYS` | Delete the files. |

**See what a value would delete first.** `npx tsx scripts/retention-prune.ts` reads the same keys and prints one line per store: how many rows or files the current values would delete, how many are old but kept because something still needs them, and how many it refused because a link was in the way. It deletes and changes no data (opening the database can create SQLite's own `-wal` and `-shm` files beside it). Try a value for one command with `RETENTION_MESSAGES_DAYS=180 npx tsx scripts/retention-prune.ts`. `--apply` deletes at once instead of waiting for the daily run.

**What the prune will not do.** It deletes only in the tables and folders named above. Files are found and removed through `src/host-fs-safety.ts`: a folder that is a link is refused, and a link or a hard-linked file where a file should be is left alone, so a link planted by a container cannot point a delete at another path. The check and the delete are two steps, so a container that swaps a folder for a link between them is not excluded (the same limit that file states for every host write). The prune was tested with files and a database made by the tests; it has not been run on a deployment with real data.

**It is not an erasure of one person's data.** The windows are by age, not by person. Copies of the same text remain in the program repo, in the audit log, at the outside parties, and in backups you make.

**3. The program repo and the audit log: no automatic deletion, by design.** No code deletes anything in the program repo: mail copies, `.eml` originals, extracted attachment text, the audit log, triage reports. No retention key applies to them and none is planned. They are a record with git history, and an automatic delete would be a delete from the newest version only.

To remove one person's mail by hand, in order of cost:

1. **Remove the files and commit.** Delete the Markdown copy, the `.eml`, and each `<mail>-<attachment>.extracted.md` under `discussions/raw/`, and commit as an admin author. Search for the person's address in the rest of the repo too: the audit log entries for that mail, `discussions/kb-triage/`, decisions and action items quote or name it. This removes the text from the current version and from what the agent reads after its next pull. **It does not remove it from history.** Anyone who can read the repo can still read every earlier version, on the git host, in the host's checkout, host repo and read mirror, and in every clone.
2. **Rewrite history.** This is the only way to take the content out of the repository itself, and the repo has no tool for it. It means: stop the bot and the intake service; rewrite every commit that holds the files (for example with `git filter-repo`); force-push to the git host; ask the git host to remove its cached copies and unreachable commits (each host has its own procedure, and some keep them for a period you do not control); delete and re-create the three copies on the bot's host (the checkout at `PROGRAM_REPO`, the host repo at `PROGRAM_HOST_REPO`, the read mirror at `PROGRAM_READ_MIRROR`), because a rewritten branch no longer matches them and each still holds the old history; have every person and every CI job with a clone delete it and clone again, since any old clone still holds the content and can push it back. What it breaks: every commit id after the first rewritten commit changes, so links to commits, the commit that first added each `.eml` (which the host checks, `INTAKE_GIT_AUTHOR_EMAIL`), and any signed or externally recorded commit id no longer match; and the audit log stops being evidence of what happened, because the same operation that removed one mail could have removed or changed anything else. Record the rewrite itself (who, when, which paths, why) somewhere that is not the rewritten repo. Not tested here: this procedure has not been run against this code.
3. **Keep the record and restrict who can read it.** Leave the history as it is and reduce the readers of the program repo to the people who must have it (see "Who can read the audit log and the raw mail"). This keeps the audit trail whole. It does not satisfy a request or a rule that requires deletion; whether it is acceptable is a decision for the office that owns that rule.

**The audit log's own rule.** `SPEC.md` section 6: entries are appended, and "do not edit the log" is a rule whose check is git history. The log is "what survives when a container is destroyed, and it is what a reviewer reads". Deleting entries, by a retention window or by hand, conflicts with that purpose: a log that sheds entries cannot show that nothing was removed. So the code sets no retention period for it, and the period is yours to set. If your institution has a records schedule, ask its records office which one applies to this log; the answer may be a minimum as well as a maximum. If the answer is a maximum, the removal is the manual procedure above, with its costs.

**Mail from senders who are not on the allowlist is stored.** The intake service commits every message to the program repo before it calls the host, and the host checks the allowlist after that (`src/channels/webhook.ts`). For a blocked sender the host writes the address and the subject to the audit log (`logDroppedEmail`), sends one "access closed" reply if the sender is on the institution's domain (rule G17; it reads the stored `.eml` first to rule out an automatic reply), and removes nothing. This is the behaviour today and it is unchanged. Two alternatives exist and neither is implemented:

- *The intake service drops the mail before it commits.* It would have to read the allowlist itself (a second reader of that file, with its own credential and its own idea of what "on the list" means). The host would never hear of the message, so there would be no audit entry for the attempt and no "access closed" reply to a colleague.
- *The host removes the stored copy after it has logged the drop.* The audit entry and the reply stay. The files remain in git history (see 1 above), the host would commit deletions of mail files, which it does not do today, and the removal runs after the agent's checkout may already have pulled the mail.

Kept as it is by delegation on 2026-11-20, for the owner's review; the choice is open in issue 66 of this repo ("Blocked senders' mail: store it, drop it at intake, or remove it after logging").

Copies outside your control are not reached by any of this: the model provider, the mail provider, the intake service's provider and Telegram each keep data under their own terms. Read those terms, or the agreement your institution has signed, for the retention that applies.

## The container's network

Two settings decide what the container can send out (`src/container-runtime.ts`, `src/web-tools.ts`).

`CONTAINER_NETWORK` has two values:

- `restricted`: the host puts the container on a Docker network created with `--internal`. The container reaches the host's credential proxy. It reaches no outside host, by name or by address, not the git host, and it gets no answer for outside DNS names. This is the default on Docker Engine on Linux, and was checked there with real containers on 2026-11-20 (Docker 29).
- `open`: the runtime's default network. The container can open a connection to any internet host. The agent has a shell and reads mail written by other people; a message that tricks it could make it send what it can read (the program repo, with the raw mail and the allowlist) to an outside address. The delivery gate and the audit log do not see this traffic. The host logs a warning at each start. This is the default on Docker Desktop (macOS, WSL), where `restricted` was not verified.

`AGENT_WEB_TOOLS` is off unless set to `1`. Off, the agent is not given web search or web fetch, and the credential proxy is the boundary for what the container can ask the model provider to do outside. The proxy reads every request the container sends (the container holds its run's proxy token and could write any request). It refuses a web search or web fetch tool at any depth of the request, a remote MCP server, an image or document given as a URL, and the provider's managed agents API. On a model path it refuses a body it cannot read as JSON; it refuses any body with a content encoding. A body it read is sent on re-serialised from what it checked. The same check runs on the Anthropic route and the Foundry route. On, a web search query goes to the model provider even when the network is restricted, and none of these checks run.

The proxy forwards only the model paths (`/v1/messages` and below, `/v1/complete`), the model list and the OAuth key exchange. The provider's host serves many other paths, and the proxy adds the host's credential to what it forwards, so every other path is refused and named once in the host log.

What that check does not cover: for tool types it refuses what is known to reach outside hosts, from the type definitions of the pinned SDK (`@anthropic-ai/sdk` 0.93.0); it is not an allowlist of tool types. A tool type the proxy does not know is forwarded, with one warning in the host log naming it. Checked on 2026-11-20 with real agent containers on the restricted network against a local stand-in for the provider, in API-key mode and OAuth mode: the SDK sent only `POST /v1/messages`, with no content encoding and only tools of its own, and the turn completed. None of it was run against a live provider, and Foundry was not run in a container.

What `restricted` does not block:

- Everything in the agent's session still goes to the model provider. That is the first row of the table above.
- **Host services that listen on all interfaces can be reached from the container** on the network's gateway address. The webhook listener's code default is all interfaces. Set `WEBHOOK_HOST=127.0.0.1`; the host logs a warning at each start while the network is restricted and that address is not loopback.

Check your own host with `npx tsx scripts/check-container-egress.ts`. Also:

- Keep the allowlist short, because allowlisted mail is the main way text reaches the agent. Remember that the agent also reads mail that an allowlisted sender forwards, and attachments.

One path out of the container is closed in the code: the host's own git. The agent can write its checkout's `.git/config` and hooks, and until 2026-11-20 the host ran git there, so a tricked agent could have had a program run on the host, with the host's network and git credential. The host now runs git only in a repository that no container mounts, and pushes only to the origin in the host's settings (`src/host-repo.ts`; `SPEC.md` section 11 lists what remains).

## What the allowlist does and does not protect

It does:

- Stop a sender who is not listed from getting an answer on email and Telegram. That sender's message is not handed to the agent.
- Limit email recipients to listed addresses, with the exceptions in `SPEC.md` section 11.
- Refuse every chat sender when the chat sender allowlist file is absent or invalid (`src/sender-allowlist.ts`; `AGENTS.md`, safety items).

It does not:

- Keep a blocked sender's mail out of the program repo. The intake service commits it before the host checks (see the table). The host then also writes the sender's address and subject to the audit log.
- Apply to web chat. Any caller with the shared secret is answered.
- Verify identity beyond what the mail headers and the intake service provide. Ask your mail administrator what sender checks (SPF, DKIM, DMARC) the intake path enforces.
- Limit what a listed sender may write about. A staff member can send mail that names a student, quotes a grade or attaches a roster. That text is then stored and sent on exactly as the table describes. The code has no filter for kinds of data.
- Limit who reads the record. That is repo access (above).
- Limit the agent's network (above).

## Decide before go-live

Take the table to the people who approve data use at your institution. Get an answer to each line, and write the answers in the program repo's governance file.

- [ ] Which classes of data may reach each outside party in the table. Until you have that answer in writing, treat the answer as "none beyond ordinary staff correspondence".
- [ ] Which model endpoint is approved, and whether the reply sensor's destination (it follows the agent's first provider unless `SENSOR_PROVIDER` says otherwise) is approved too.
- [ ] Whether the reply sensor may also read email replies (`SENSOR_EMAIL_REPLIES=1`). Off by default: it sends each email reply and the start of the mail it answers to the sensor's destination.
- [ ] Which mail provider and intake service are approved, and what they retain.
- [ ] Whether Telegram is approved for operator alerts that carry addresses and subject lines.
- [ ] Who may read the program repo, who reviews that list, and how often.
- [ ] How long the audit log and the raw mail are kept, and who performs a removal.
- [ ] Whether the stores on the host get a retention window (the `RETENTION_*_DAYS` keys), and how many days. Unset, they are kept forever.
- [ ] What senders are told about where their mail goes (`AGENTS.md`, ASK 5).
- [ ] Whether the agent gets web tools (`AGENT_WEB_TOOLS`) or an open network (`CONTAINER_NETWORK=open`). Both are off by default on Docker Engine on Linux.
- [ ] Whether state snapshots are used, and to which repo they go.
- [ ] Who owns each account the bot depends on (model, mail, domain, git, hosting, Telegram), as a role and not a person, and what happens to them when the operator leaves ([`service-ownership.md`](./service-ownership.md)).

**A conservative default for a first pilot:**

- Staff senders only on the allowlist. No students, no public address.
- No student records. Tell the senders in writing not to send or forward mail that identifies a student, grades, accommodations, conduct or health matters, and not to attach rosters. This is a rule for people; the code cannot enforce it. Say what to do when it happens anyway: who is told, and who removes the mail.
- The reply sensor off (`BEHAVIOUR_SENSOR_DISABLED=1`) unless its destination is approved, and `SENSOR_EMAIL_REPLIES` unset.
- Email and one Telegram admin chat. Web chat off. `/remote-control` not used.
- A private program repo whose readers are the pilot team and the operator.
- `LOG_LEVEL` at its default.
- The example snapshot scripts not run.
- `AGENT_WEB_TOOLS` unset and `CONTAINER_NETWORK=restricted` (the defaults on Docker Engine on Linux), with `scripts/check-container-egress.ts` passing on the host.

This default narrows what the pilot touches. It is not a finding that the pilot complies with any law or policy. For questions about student-record law (in the United States, FERPA), ask your registrar or your institution's privacy office and counsel; for vendor approval, ask your IT security or procurement office.
