A coordinator for your team, and the record it keeps.

ProgramOS is a bot that answers your team's questions by email, from a git repository that is the team's source of truth. It cites the file behind each answer. It writes down decisions, action items and open questions as they happen.

Clone it on GitHub How to start

The code is a close copy of a coordinator that has been tested in production with one program since April 2026. It is open source under the MIT license.

What it does

One place where questions get answered from the record.

It is for a team that runs a project, a program, a grant, a lab or a unit. The knowledge base is a plain git repository of Markdown files that your team owns.

Answers with citations

It searches the repository and replies with the file path behind each statement. It does not invent content.

Records what the team decides

Send it a status update. It extracts decisions, action items and open questions, and commits them.

Sends reminders

Scheduled jobs remind owners of action items and send regular summaries.

Routes approvals

A change that needs a person's approval goes to the person who has that authority, and waits for the answer.

Checks replies before they are sent

A delivery gate on the host inspects each reply. A reply that fails is held, and the operator is told.

Keeps an audit log

Accepted messages and replies are written to a log in your own repository.

How a message moves

The agent works in a container. The host decides what leaves.

  1. Message arrivesEmail, or Telegram for the admin.
  2. Allowlist checkOnly listed senders get an answer. The list is a file in your repository.
  3. Agent in a containerIt sees only the folders you mount. Your credentials stay on the host.
  4. Delivery gateThe host checks the reply and its recipients.
  5. Reply and recordThe reply is sent. The repository and the audit log are updated.

Where the code comes from

What was tested in real use, not a rewrite that nobody has run.

The code is a close copy of K-ai, a coordinator for one online master's program. K-ai has been tested in production with one program since April 2026.

Content removed, code kept

The program's people, addresses, policies and history were removed. The code was not redesigned.

The same tests pass

The 1,761 tests that pass in K-ai pass in this repository. This repository adds 879 more, so 2,640 tests run on every change.

It stays current

K-ai stays the source. This repository takes its changes through a repeatable export.

Start

Clone it. Your coding agent does the adapting.

You need a host that can run Docker, a mail address for the bot, a git host for the knowledge base, and an AI service that your organization allows your mail to reach. Check that last point first.

  1. Clone the repository. 
    git clone https://github.com/vishalsachdev/programos.git
  2. Open it with your coding agent (Claude Code, Codex, Cursor or another) and say: 
    Read AGENTS.md and help me adapt this for my project.
  3. The agent first asks whether you are setting this up at the University of Illinois or somewhere else. That picks the pages it uses with you: the Illinois track or the general track. The code is the same on both.
  4. The agent explains three ways to start and asks which you want: try it (one person, a laptop, Telegram only), a pilot (a small always-on machine, email, a handful of allowlisted colleagues; the recommended first version), or institutional (the same on services your institution has approved).
  5. The agent asks you six policy questions before it changes anything: which AI service is allowed, who approves, which address the bot uses, where data lives, what senders are told, and which channels you want. It asks one thing at a time and writes your answers down.
  6. It creates your knowledge-base repository, fills in the settings, and keeps the tests passing.
  7. You review a test exchange. You decide when to deploy.

Safety

Numbered rules, each with the failure it prevents.

The bot works under a set of numbered governance rules. The code, the prompts and the tests cite the rule numbers. Role and access changes are made by the admin only, never because a message asked.

Where the guarantees stop

  • The person allowlist holds for email and Telegram. Web chat checks a shared secret only.
  • On email the allowlist is matched on the From header, which a sender can forge. By default the host only records whether named mail servers confirmed the sender; it can be set to drop mail they did not confirm. Never run against live mail.
  • Use Telegram with one chat only. With two or more chats, a reply can go to the wrong chat.
  • Sender caps apply to email only, and they reset when the process restarts.
  • Email needs a separate intake service. The one in the repository is new and has not run against live services.

The full list is in SPEC.md, section 11. Read it before you rely on a rule.
